# Research: multi-client agent-session architecture

Checked 2026-09-20 against the installed `@earendil-works/pi-coding-agent` 0.85.1 and public upstream repositories.

## Verdict

**A. Remote Pi has concurrent mobile-client fan-out, but it is not a general shared-session daemon that Pi TUI, pi-web, and arbitrary clients can attach to.** A paired app can `session_sync`, receive replay, and share one extension-owned Pi process with other paired app owners; app-originated messages are echoed to every active owner. Its local multi-terminal feature is a separate agent-to-agent UDS mesh, not multiple presentations of one Pi conversation. No documented protocol lets a TUI or pi-web attach to a daemon's in-memory `AgentSession`; the extension's own `(cwd, name)` UDS lock deliberately prevents a second default Remote Pi participant. [Remote Pi protocol](https://github.com/jacobaraujo7/remote_pi/blob/main/PROTOCOL.md) [Protocol types](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/protocol/types.ts) [CWD lock](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/session/cwd_lock.ts)

**B. Pi will probably move toward solving this, but it is not usable as a pi-web dependency today.** Version 0.85.1's supported SDK and `pi --mode rpc` have no attach-to-existing-process API. In parallel, upstream has an explicitly experimental `pi-server`/`pi-client` design whose server supports multiple presentation attachments to one Session, subscriptions, attachment IDs, and a single worker-owned writer. Pi 0.85.1 then deliberately withdrew that code from the supported npm surface; 0.86.1, released today, still has not promoted it. Do not wait for it, but avoid a large private protocol that would make migration to it painful. [0.85.1 changelog](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/CHANGELOG.md) [Experimental server](https://github.com/earendil-works/pi/blob/v0.85.1/packages/server/README.md) [0.86.1 changelog](https://github.com/earendil-works/pi/blob/v0.86.1/packages/coding-agent/CHANGELOG.md)

## Confirmed facts

### 1. Remote Pi

- **Ownership and trust boundary.** The mobile app and the Pi extension connect to a Rust WebSocket relay. The extension owns the live Pi runtime; the relay routes connections and persists only Owner-signed mesh-membership metadata in SQLite. Ed25519 authenticates connections and signed Owner blobs authorize Pi-to-Pi routes, but current App↔Pi payloads are plaintext inside TLS: the relay operator can inspect them. Owner co-membership also does not prove that an Owner paired with or controls either Pi key. Self-hosting moves that operator boundary under the user's control. [Root README](https://github.com/jacobaraujo7/remote_pi/blob/main/README.md) [Relay trust model](https://github.com/jacobaraujo7/remote_pi/blob/main/relay/README.md) [Canonical protocol](https://github.com/jacobaraujo7/remote_pi/blob/main/PROTOCOL.md)

- **Wire protocol.** App↔extension traffic uses a relay-routed outer `{ peer, ct }` envelope, where `ct` is base64 JSON rather than end-to-end ciphertext. Inner app commands include `pair_request`, `user_message`, queue changes, cancellation, `session_sync`, typed model/session actions, and extension-UI responses. Server frames include echoed `user_message`, `agent_chunk`, `agent_done`, final `agent_message`, tool events, `session_history`, queue state, action responses, and `bye`. Pi-to-Pi mesh traffic is different: a JSONL `{ from, to, id, re, body }` envelope on local UDS, with `pi_envelope` / `pi_envelope_in` frames for cross-PC relay forwarding. [Protocol types](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/protocol/types.ts) [Peer channel](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/transport/peer_channel.ts) [Canonical protocol](https://github.com/jacobaraujo7/remote_pi/blob/main/PROTOCOL.md)

- **Replay and fan-out exist for paired app clients.** `session_sync` returns `session_history`; the protocol types say app-originated user messages are echoed to every connected owner so all owners share one timeline. The project changelog calls this a multi-channel extension and says it accepts multiple paired Owners through an active-peer map. It also broadcasts Android-owned queued state to all owners. This is real multi-subscriber behavior for Remote Pi's app protocol. [Protocol types](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/protocol/types.ts) [Changelog](https://github.com/jacobaraujo7/remote_pi/blob/main/CHANGELOG.md)

- **It is still not a generic attach protocol.** The app has pairing and `session_sync`, then transport close or a `bye` frame. It has no public arbitrary-client attach/detach capability keyed by a Pi JSONL session, nor a raw Pi event stream. It projects selected chat, tool, model, and extension-UI events. The README's “two Pi terminals” claim means separate Pi agents joining an agent-network room over UDS; it does not claim that two processes share one Pi `AgentSession`. [Extension README](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/README.md) [Protocol types](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/protocol/types.ts)

- **Daemon mode does not make the TUI a client.** The supervisor starts one `pi --mode rpc` child per daemon cwd and writes prompts to that child's stdin. Its documented workflow pairs through an interactive Pi first, then stops it before starting the daemon. Its troubleshooting guide says another Pi process in that cwd causes the extension's cwd lock to reject the second participant. The lock is kernel-enforced by a UDS/named-pipe bind, scoped by `(cwd, name)`; a different name creates another Remote Pi room, not another presentation of the daemon's runtime. [Daemon plan](https://github.com/jacobaraujo7/remote_pi/blob/main/plan/26-daemon-mode.md) [Daemon guide](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/docs/daemon.md) [CWD lock](https://github.com/jacobaraujo7/remote_pi/blob/main/pi-extension/src/session/cwd_lock.ts)

- **Maturity and licence.** The root `LICENSE` and the extension's `LICENSE` are MIT. The root README still says a repository-wide licence decision is pending, which is stale or contradictory legal copy worth resolving before vendoring individual components. The repository had a commit on 2026-09-19 and its latest GitHub release is a Cockpit release from 2026-09-16; the original all-project `v0.1.3` release was 2026-05-22. Major mesh work remains under `Unreleased`, and the protocol asks operators to roll out Relay 0.3 before Extension 0.6 because mixed wire labels are only partly interoperable. Treat the protocol as actively changing, not stable infrastructure. [Root licence](https://github.com/jacobaraujo7/remote_pi/blob/main/LICENSE) [Repository activity](https://api.github.com/repos/jacobaraujo7/remote_pi) [Latest release](https://github.com/jacobaraujo7/remote_pi/releases/tag/cockpit-v1.28.33) [Changelog](https://github.com/jacobaraujo7/remote_pi/blob/main/CHANGELOG.md)

### 2. pi-web's upstream position

- **The checked-out repository is a fork of `agegr/pi-web`; its Git config names `zochari/pi-web` as `origin` and `agegr/pi-web` as `upstream`.** `agegr/pi-web` itself is not a fork. [Local Git config](/home/lpzchr/repos/pi-web/.git/config) [Upstream repository](https://github.com/agegr/pi-web)

- **#632, “pi-web UI does not auto-refresh when Pi session output changes,” is closed as not planned.** The maintainer said browsing and resuming session files is supported, but concurrent use of one session by Pi and pi-web is not: each process owns in-memory state, and live bidirectional sync would need cross-process coordination and conflict handling that they do not plan to add. [Issue #632](https://github.com/agegr/pi-web/issues/632#issuecomment-5620295981)

- **#796, “fix: see sessions written by another pi process,” was merged on 2026-09-18.** It detects a new on-disk entry only while pi-web's wrapper is idle, destroys that stale wrapper, and reloads from disk. The maintainer approved it as a narrow read-visibility fix. The PR explicitly preserves the unsupported case: an external writer during a live pi-web run. [PR #796](https://github.com/agegr/pi-web/pull/796) [Maintainer review](https://github.com/agegr/pi-web/pull/796#pullrequestreview-5223003017)

- **#795, “Reading a session that another pi process is writing,” remains open without maintainer comment.** Its contributor proposes focused-session read following and explicitly excludes cross-process write coordination. It is useful evidence of the remaining behavior, not a maintainer commitment. [Issue #795](https://github.com/agegr/pi-web/issues/795)

- **No searched issue established file corruption as the current failure mode.** The documented problem is divergent in-memory state and stale reads. Simultaneous writers may append children from different stale leaves, creating unexpected branches; neither Pi nor pi-web currently serializes that choice.

### 3. Installed upstream Pi 0.85.1

- **Supported RPC is one spawned process's stdin/stdout stream.** `pi --mode rpc` accepts line-delimited JSON commands on stdin and emits responses and agent events on stdout. It streams rich agent events to the one controlling host and accepts queued `steer`/`followUp` prompts, but the documented protocol has no listener registration, client identity, attach command, or event fan-out facility. This establishes a single-process controller model rather than a multi-client server. [Local RPC documentation](/home/lpzchr/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md) [0.85.1 RPC documentation](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/rpc.md)

- **The supported SDK only subscribes to an in-process `AgentSession` object.** `createAgentSession()` constructs a session; `session.subscribe()` subscribes to that object. `SessionManager.open()` loads a JSONL file into one manager. No documented supported SDK method attaches to a session owned by another Pi process or subscribes to its events. [Local SDK documentation](/home/lpzchr/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/sdk.md)

- **There is no session-file single-writer or external-change machinery in the installed `SessionManager`.** The module builds its index when loading, retains its own `fileEntries` and leaf, appends entries via `appendFileSync`, and sometimes rewrites the file using `openSync(..., "w")` plus `writeFileSync`. It imports no lock implementation and contains no file watch or mtime revalidation. It skips malformed partial lines during reads, which helps a reader survive a torn tail, but it is not a concurrency protocol. [Installed SessionManager](/home/lpzchr/.local/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/session-manager.js) [Session format](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/session-format.md)

- **Upstream already has the right architectural experiment.** `pi-server` documents multiple presentation attachments for one durable Session, each with a server-generated attachment ID; it provides scoped service subscriptions and keeps worker ownership of the session writer. `pi-protocol` defines session routes containing `serverId`, `sessionId`, and `attachmentId`, plus attach/detach, correlated calls, and subscription updates over CBOR frames. This is much closer to the required ownership model than Remote Pi. [Experimental server](https://github.com/earendil-works/pi/blob/v0.85.1/packages/server/README.md) [Experimental protocol](https://github.com/earendil-works/pi/blob/v0.85.1/packages/protocol/README.md) [Client-coordination PR #7409](https://github.com/earendil-works/pi/pull/7409)

- **That experiment is explicitly unsupported and not a current migration target.** The 0.85.1 release says experimental client/plugin subpaths and server/client commands became source-only through `pi-test.sh`; the supported local SDK and stdio RPC stayed unchanged. The published package excludes `dist/client` and `dist/experimental`, lists `pi-client`, `pi-protocol`, and `pi-server` only as dev dependencies, and the experimental protocol states that it has no compatibility guarantees and no authenticated transport context. Pi 0.86.1, published 2026-09-20, retains the same package arrangement and does not announce promotion. [0.85.1 changelog](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/CHANGELOG.md) [0.85.1 package manifest](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/package.json) [0.86.1 package manifest](https://github.com/earendil-works/pi/blob/v0.86.1/packages/coding-agent/package.json) [0.86.1 release](https://github.com/earendil-works/pi/releases/tag/v0.86.1)

## Inference and consequence

- **Remote Pi is useful as a reference for relay authentication, paired-mobile replay, and fan-out.** Reusing its protocol wholesale would tie pi-web to a rapidly changing, mobile-specific vocabulary and still leave the hard boundary unresolved: pi-web and the TUI must send commands to one runtime owner rather than open the same JSONL in two runtimes.

- **A safe pi-web design needs one runtime owner and multiple presentation clients.** The owner should serialize mutating operations, emit an ordered event stream to subscribers, provide a snapshot/replay cursor for reconnect, and own session-file persistence. The browser, mobile app, and eventual TUI adapter become presentations. File watching is only a read-follow fallback for legacy external TUI processes, never the correctness mechanism for concurrent commands.

- **The upstream experiment is a migration signal, not a delivery promise.** It demonstrates clear intent and substantially overlaps the needed model, so pi-web should isolate any new daemon/client contract behind a small adapter. It does not justify deferring work: the released 0.85.1 and 0.86.1 interfaces still leave pi-web with only SDK-in-process ownership or a one-controller stdio RPC child.

## Gaps

- I found no published commitment, target release, or TUI integration plan for promoting Pi's experimental server/client stack.
- I found no Remote Pi contract for making an existing interactive TUI attach to a daemon-owned runtime.
- I did not run an interoperability test with multiple real Remote Pi app clients. The source and protocol documents confirm fan-out and sync semantics; production behavior still needs an end-to-end test before adoption.
